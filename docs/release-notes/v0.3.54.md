# Jiva v0.3.54 — Parallel Tool Execution, OpenRouter Provider Routing, Session Restore Fix, Container Persona Support & Documentation Restructure

## New: Parallel tool execution

When a model returns several tool calls in one response, independent calls now run concurrently. This applies in code mode (including plan mode), in the general-mode Worker, and in the evaluator harness. Previously every call was awaited one by one. See [Parallel Tool Execution](../reference/TOOL_EXECUTION.md).

- **Shared scheduler (`src/core/tool-scheduler.ts`).**
  - Each call declares its access: reads/writes on paths, or exclusive.
  - Calls are grouped in order: non-conflicting calls run together, capped by `maxConcurrency`; conflicting or exclusive calls run alone. Nothing is reordered across a conflict.
  - Results are always returned in call order.
  - One failing call doesn't affect its siblings.
- **Classification.**
  - Concurrent: reads, `glob`/`grep`, edits to different files, read-only `bash` commands (a conservative allowlist in `bash-readonly.ts`), and MCP tools whose server sets `readOnlyHint`. MCP tool annotations are now preserved for this.
  - Exclusive: everything else, including `bash` writes, sub-agent spawns, and `interact_with_agent`.
- **Ordering of loop bookkeeping.**
  - Doom-loop and read-streak checks run before dispatch.
  - Model instructions are appended after the last tool result.
  - This **fixes two existing bugs**:
    - The Worker pushed dry-run and circuit-breaker messages between tool results, which corrupted the history after pairing repair.
    - The Evaluator's doom-loop break left tool calls without responses.
- **Cancellation.** `CodeAgent.stop()` now aborts the turn: running commands are killed and queued calls are skipped.
- **Prompts.** The code-mode, plan-mode and Worker prompts, plus the `read_file`/`grep`/`glob`/`bash` descriptions, now tell the model to batch independent calls.
- **Configuration.**
  - New `toolExecution: { parallel, maxConcurrency }` setting (default `true`, `8`).
  - Env `JIVA_PARALLEL_TOOLS` / `JIVA_MAX_TOOL_CONCURRENCY`.
  - HTTP `agentConfig.parallelTools`.
  - `jiva benchmark --no-parallel-tools` for A/B runs.
- **Timing.**
  - `AgentResponse.timing` reports `llmMs`, `toolMs`, `maxCallsPerResponse`, `maxBatchSize` and `parallelSavedMs`.
  - There is a per-turn timing log line.
  - Benchmark tasks and the report now split model time from tool time.

**Measured impact:**
- Parallel execution helps only models that batch calls. On Jiva's request, GLM-4.6, Kimi K2, Claude Haiku 4.5 and Gemini 2.5 Flash do; gpt-oss-120b and Qwen3-Coder issue one call per response.
- An exploration prompt (7 reads + 2 shell commands) took GLM-4.6 2 model round-trips, with the 9 calls run 9-wide. Qwen3-Coder took 10 round-trips.
- In the taskstore benchmark, model time is about 98% of wall-clock, so further gains there need model-side work.

### Other latency fixes
- **Async file tools.** `read_file`, `grep` and `glob` now use non-blocking I/O.
- **LSP outside the file lock.** `edit_file`/`write_file` collect diagnostics after releasing it.
- **LSP diagnostics race fixed.** The listener is registered before notifying the server, so a fast server no longer forces the 3 s timeout. The timeout timer is also cleared.
- **Non-blocking title generation.** Conversation titles are generated in the background, so the first reply no longer waits for a title LLM call. Saves are serialized, so a late title never overwrites newer data.
- **Faster startup.**
  - CLI model connectivity checks run concurrently.
  - Code mode only starts the MCP servers it exposes; HTTP code-mode sessions start none.
  - Persona MCP servers start concurrently (CLI, HTTP, agent spawner).

### Tests
- New test files:
  - `tool-scheduler.test.ts`
  - `bash-readonly.test.ts`
  - `agent-parallel.test.ts` (CodeAgent and Worker loops with a scripted model)
  - `conversation-manager.test.ts`
- **Test runner fix.** `npm test` now uses `scripts/run-tests.mjs` for recursive discovery. Previously the shell-expanded glob silently skipped tests more than one directory deep.

## New: OpenRouter as a first-class provider

OpenRouter is now a built-in provider with **priority-ranked upstream provider routing**. See the
[OpenRouter guide](../user-guides/OPENROUTER.md).

- New `openrouter` block per model role (`providerOrder`, `allowFallbacks`, `only`, `ignore`, `sort`,
  `requireParameters`, `dataCollection`, `zdr`, `quantizations`, `maxPrice`, `modelFallbacks`,
  `referer`, `title`), validated by Zod and mapped onto OpenRouter's `provider` / `models` request fields.
  Routing is only ever sent to OpenRouter endpoints.
- `require_parameters` defaults on for requests with tools so providers can't silently drop tool definitions.
- Setup wizard: new **OpenRouter** preset; lists the providers OpenRouter offers for the chosen model and
  asks for a ranking and fallback policy. `jiva config --show` prints the routing.
- Responses: served-by provider/model captured (`ModelResponse.routing`), `cost` / cached / reasoning
  token details parsed, cost accumulated by `TokenTracker.totalCostUsd`.
- Errors: failures delivered inside an HTTP 200 body or mid-stream are now surfaced; `402` is non-retryable with
  guidance; `408` retried; `503`/`404` explain the active routing constraints; fewer client retries
  (OpenRouter fails over upstream itself).
- `reasoning_details` are echoed back on tool-call turns (needed by e.g. Claude via OpenRouter).
- HTTP: `JIVA_MODEL_PROVIDER_ORDER`, `JIVA_MODEL_ALLOW_FALLBACKS` (and tool-calling equivalents) env vars;
  per-session `agentConfig.providerOrder` / `allowFallbacks`.
- Generic `headers` map on any model config.

- **For embedding apps (e.g. Jivam):**
  - New public exports: the OpenRouter helpers (`fetchOpenRouterModels`, `fetchModelProviderEndpoints`, `OpenRouterConfigSchema`, …), `modelClientConfigFromStored`, `resolveToolExecutionSettings`, and the `TurnTiming` type.
  - `ModelOrchestrator.getLastRouting()` / `getProviderUsage()` / `resetProviderUsage()` report which upstream provider served each call, without parsing logs.

### Internal
- `modelClientConfigFromStored()` (`src/models/client-config.ts`) is now the single config → client mapping,
  replacing hand-copied field lists in the CLI, benchmark and HTTP session manager. Side effect: multimodal
  clients in the CLI now honour `hasVision`, `maxRequestsPerMinute` and `useGoogleADC`; `defaultReasoningEffort`
  and `includeReasoning` are now part of the stored config schema (previously stripped).
- `ModelClient.buildRequestBody()` extracted so request shaping is unit-testable.
- New tests: `src/models/openrouter.test.ts`, `src/models/model-client.test.ts`.

## Deprecations

- **`JivaAgent` is deprecated.** It is the original single-agent class, unused by the CLI and the HTTP server since v0.2.1.
  - It now carries `@deprecated` JSDoc and logs a one-time warning when constructed.
  - Use `DualAgent` (general mode) or `CodeAgent` (code mode) instead; both implement `IAgent`.
  - It will be removed in a future minor release.
  - The Quick Start and `examples/programmatic-usage.ts` now use `DualAgent`/`CodeAgent`.

## Bug Fixes

### Conversations saved under the session ID (HTTP server)
`SessionManager` now passes the session ID to `ConversationManager` as a default conversation ID, so
conversations are stored under the same ID that is used to restore the session.

Two edge cases are handled in `ConversationManager`:
- **Restored sessions keep their metadata.** The first save after a restore loads the existing
  conversation, so its title, `created` timestamp and cumulative token totals are no longer reset.
- **Resetting a conversation starts a new one.** `setCurrentConversationId(null)` also clears the
  default ID, so `resetConversation()` no longer overwrites the previous conversation with the
  session ID.

## Deployment

- `Dockerfile` copies `scripts/` into the builder stage (required by the build) and ships
  `examples/personas` to `/app/.jiva/personas` so sub-agent spawning has personas available.
- `.dockerignore` / `.gcloudignore` no longer exclude `examples/` (personas are needed at runtime).
